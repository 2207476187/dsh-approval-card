# 2026-11 开发日志

## 2026-11-03 审批卡看不到实际要动的位置

### 转折点：真正生产卡片文案的不是宿主，是审批门

一开始按「宿主提权模板只给一句 justification」去改，写出了一个改写插件，
但线上日志里最新的改写行**都没带总结** —— 说明处理器走了 `mode === ''` 分支。
把会话日志解出来才看到真实原因：`approval/asked` 的 `reason` 根本不是
`escalate sandbox to <mode>: …`，而是 `目标含工作区外路径 1 处：C:\Windows\Temp`。

### 取证方法（可复用）

会话文件 `session.v4.jsonl.zstd` 是**多帧 zstd 拼接**（每 100–200 字节一帧）。
`zstdDecompressSync` 只解第一帧，`createZstdDecompress` 直接报
`Error: Unknown frame descriptor`。可行做法：扫 `28 b5 2f fd` 偏移切片后逐帧解压再拼接
（见 `probes/probe-session3.mjs`）。一次 276 KB 的会话 → 189 条事件。

此后所有验证都走「回放」而不是「等下一次弹卡」：
`probes/probe-replay.mjs` 把历史 `approval/asked` × `tool/call` 参数喂回 `applySummaryText`，
一次跑完全部 172 个真实请求，改动前后逐条对比。

### 线上日志暴露的四个真实缺陷

1. `对 p://127.0.0.1:43189/ 进行下载` —— `PATH_RE` 的 `[A-Za-z]:[\\/]` 把 `http://` 里的
   `p://` 当盘符。
2. `对 $env:DSH_HOME\profiles\… 进行查找或读取` —— 命令里的环境变量没展开。
3. `对 当前工作目录 … 进行调用工具` —— 命令里没有绝对路径时只给了工作目录。
4. 审批门整块理由被原样附加，其中的 `路径：` 行是它按空白截断的版本，与首行重复且更含糊。

### 被否决的做法

- 直接改 `dsh-approval-gate\src\zh.mjs`：它是 `git+https://…` 安装的第三方包，更新即覆盖。
- 改程序目录里的 `dsh-client-ui-chat`：DSH 更新会重写 `X:\Program Files\…`。
- 用 `middle-ellipsis` 截短路径「让卡片好看」：看不见完整路径等于没显示，方向相反。

### 留下的坑

- confined 沙箱下 `node --test test/` 会 `spawn EPERM`，只能 `node test/text.test.mjs` 直接跑。
- 运行中的模块不会因文件变化重载，每次改动都要重启 DSH 才能看到效果。

2. `profiles/desktop/cordis.patch.yml`：删掉原来的 `insert`（否则同一插件挂两遍），改由插件
   自己的 `dsh.bundle.patch` 加载。
3. `plugins/dsh-approval-card/cordis.patch.yml`：`name` 从 `./src/index.mjs` 改成裸包名

### `pnpm install` 在这台机器上不可用（既有病态）

```

```

`billion-context@0.1.212` 已从 registry 消失，而它写死在 profile 依赖里，所以**任何**

## 2026-11-04 插件显示名 = 审批卡片

包名 / 目录 / patch `id` 保持 `dsh-approval-card` 不动 —— 它是模块说明符，被
`node_modules` junction、`dsh.profile.bundles`、bundle patch 的 `insert.name` 三处引用，
改名字只会换来一串同步改动，列表里看不见任何差别。

显示名走宿主约定的 locale 资源（`dsh-app-boot` 的 `readPluginMeta`）：
`locale/en.json` 是锚点（缺它整目录不读），`locale/zh.json` 提供中文；
形状 `{"meta":{"title","description"}}`，且必须能被 `${specifier}/locale/<lang>.json`
解析到 → `package.json` 的 `exports` 要加 `"./locale/*": "./locale/*"`。
插件管理页用 `pkg.meta?.title ?? pkg.name`，所以现在显示「审批卡片」。

### 一个不属于本插件、但值得记录的观察

同一 `callId` 会出现**两张卡**：审批门先转人工（`reason=目标含工作区外路径…`），
放行后工具的沙箱提权再问一次（`displayReason=允许本次操作使用 … 权限：…`）。
当前会话 240 个调用里有 **75 个（31%）** 是这种情况。
根因在 `permission` 预设（`auto-approve` 的 `sandbox: workspace-write` + `approval: ask`）
与审批门的转人工出口叠加，不是文案层能消除的；要减少只能动预设或门的自动放行规则。

### 决定：重复的卡不合并，让第二张自报序号

三个候选都试算过代价：
① `sandbox: danger-full-access` —— 只剩一张卡，但丢掉文件系统围栏这层兜底；
② 门侧 `outsideNeedsHuman: false` —— 也只剩一张卡，但「路径跑出工作区」不再人审，
而且那个开关在别人仓库的包里，更新会覆盖；
③ 文案层标记 —— 两张卡照旧，但第二张写明「同一次操作的第 N 个审批请求」。

选 ③：零权限面变化、不碰别人的包、不依赖预设。实现是 `nextAskOrdinal`（`src/index.mjs`，
按 `callId` 计数）+ `markRepeatOrdinal`（`src/text.mjs`，幂等追加记号）。

一个关键取舍：**只数真的流到本插件的请求**。被上游（审批门/Flash）直接答掉的请求到不了这里，
用户也看不到它的卡；若按会话日志里的 `approval/asked` 计数，就会给唯一那张可见的卡标上
「第 2 个」，反而误导。

验证：单测 28 条全绿；回放最新会话 354 条 `approval/asked` → 354 条改写、86 条带序号、
`reason` 0 条被改（`probes/probe-ordinal.mjs`）。改动需重启 DSH 生效。

### 「这个目录为啥也要我审批」：路径在空格处被截断

用户问：改 `docs/devlog/2026-11.md` 明明在工作区内，为什么还要审批。查下去发现是审批门自己的
路径提取 bug，不是工作区边界配置问题：

- `auto-approve\events.jsonl` 那条记录自相矛盾 —— `files` 是完整路径，`targets` 却是
  `["D:\\DeepSeek"]`，`targetScope: "outside"`。
- 根因：`resolveToolCallTargets()`（`dsh-approval-gate\src\index.mjs:480`）把结构化字段
  `file_path` 也交给 `extractAbsolutePaths()`。那套词法（`ABS_PATH_TOKEN_RE`）是给**命令文本**用的，
  遇空白即停；给 `'C:\Program Files\…'` 准备的引号分支对不带引号的单条路径不生效。
  于是 `D:\DeepSeek Harness工作目录\…` 被截成 `D:\DeepSeek` → 不在工作区之下 → 判「工作区外」。
- 直接调官方模块复现：`isWithin(ws, target)=true`，但
  `extractAbsolutePaths(target)=["D:\DeepSeek"]`，`classifyPathScope(那一条)` → `outside`，
  而 `classifyPathScope([完整路径])` → `inside`。
- 这也解释了「为什么只有部分操作被打断」：`pwsh` 命令里路径基本带引号，走引号分支能取全；
  `edit`/`write` 的 `file_path` 不带引号，必截断。
- 顺带一个同源现象：某次卡片的原因写成 `目标含工作区外路径 1 处：/plugins/` —— 正文里的
  `/plugins/<包名>/…` 被同一个提取器当成 POSIX 绝对路径收了进来。

决定（见 `docs/adr/0002-本地补丁修审批门路径截断.md`）：不降安全姿态去关 `outsideNeedsHuman`，
而是给门的这一个函数打本地补丁 —— 结构化字段直接当一条路径，命令类字段仍走文本提取。
补丁做成 `tools/patch-approval-gate.mjs`：幂等、锚点不唯一就放弃、写前备份、写完 `node --check` 失败回滚，
更新依赖后重跑一次即可。

踩到两个小坑：① 脚本里把带反引号的路径写进模板字符串 → 语法错误，注释里不能出现反引号；② 门源码是 CRLF，锚点用 `\n` 拼就一处都匹配不上 —— 不能为了匹配去改整份文件的换行，
改成按文件检测出的 EOL 拼锚点。③ 时间戳 `replace(/[-:T]/g,'')` 会把毫秒前的点留下，
备份名变成 `…101900.`，Windows 上这个尾点还改不动，得用 `\\?\` 前缀的 `File.Move` 才能重命名。

补丁第一版把结构化字段一律标成 `kind: 'data'`，读代码时发现这会把
`X:\Program Files\DeepSeek Harness\…`、`C:\Windows\System32\…` 从「程序路径」降级成「数据目标」，
于是读 DSH 自己的程序文件反而变成越界 —— 修完第一个 bug 顺手造出第二个。
改成按 `paths.mjs` 的口径分档（device / program / data）后重打一遍。

验证不靠重启：`probes/probe-gate-patch.mjs` 把补丁函数从门源码里原样抠出来，
用真实的 `extractAbsolutePaths` / `classifyPathScope` 跑 9 个用例，全部通过 ——
含「工作区内的带空格路径 → inside」（原来的病根）、「Program Files / System32 → program，不参与定域」、
「`/proc/cmdline` → device」、「UNC 与 POSIX 根 → outside」、「`~/.ssh/id_rsa` → outside」
（这条最关键：修 bug 不能把真正该拦的也放过）。

重启后（18:24 启动）真机验证：

- 在工作区内新建 `probes/fixtures/scope-check.txt`（`write`，结构化 `file_path`）→
  `events.jsonl` **没有任何事件**，也没有弹卡：定域放行层直接过了。
- 对同一文件再做一次 `edit` → 同样没有事件。
- 同期 pwsh 事件的 `targets` 变成完整路径
  `D:\DeepSeek Harness工作目录\DeepSeek\probes\fixtures\scope-check.txt`，
  再没有 `D:\DeepSeek` 那种被空格切断的残片 —— 补丁确实在跑。
- 这段时间唯一还会转人工的是 `sensitive-path`：命令读了
  `C:\Users\<user>\.dsh\auto-approve\events.jsonl`（审批门自己的数据目录）。
  那是门的自保规则，与本 bug 无关，属预期。

### 2026-11-04 19:1x 首行改为罗列全部目标

三目录的卡在真机上跑出来了，首行如预期把三条路径全列在「对 … 进行」之间。但第二张（提权卡）


`\\?\$p` 被当成目标写进首行，`'C:\tmp exists={0}' -f …` 这种格式串也被收。加 `JUNK_PATH_RE`
（`$ % { }` 或 `\\?\` 开头）在 `targetListFor` 的 `push` 与 `looksLikePath` 两处拦掉。

## 决定：重复的字段留信息更全的那个

用户看到第二张真卡后直接给了取舍：`命令：` 不要（首行已经说清目标）；`原因：` 与 `理由：` 重复，

### 复核：三条裁剪规则紧度不一样

用户要求「命令行不要、原因与理由重复留理由、权限与影响重复留影响」。第一版把后两条写成
标签判断（有 `理由：` 就丢 `原因：`、有 `影响：` 就丢 `权限：`），单测 32、36 立刻挂：
「宿主只给 escalate 文本、没有 displayReason」那种卡根本没有影响行，`权限：` 是唯一
说明放宽边界的一行，却被当成重复删掉了。

改成内容判定：

- `原因：` 只有与某条 `理由：` **值相同**才丢 —— 门记的原因和宿主模板里的理由偶尔不是同一句；
- `权限：` 只有 `影响：` 里出现「整机 / 任意路径 / 系统位置」才丢 —— 那时影响行已经说清

唯一的信息来源。

## 第二张卡只剩首行：同一请求被问了两次

触发点：21:41 让用户看卡，第 1 张写全、第 2 张只剩首行 + 序号。

排查：把「同一 req 连喂两次」这个假设做成单测才复现 —— 第一次返回 `对 … / 权限：… / 理由：…`，
第二次把这段放进 `requestedModeOf` 之外当作既有 `displayReason.zh`，输出就只剩 `对 …`。

机制：`applySummaryText` 里 `if (!hasSummary(rawZh)) parts.push(summary)`，
一旦第一次写过总结，第二次直接不拼任何行；`理由` 分支又有 `!hasZh` 的否定条件，
于是两张卡的第二张**必然**是残的，且只在「门先问一次」的链路上出现（第二张卡正好是这条）。

改法：`hasSummary(rawZh)` 时按行补齐（`for (const line of summary.split('\n').slice(1)) if (!rawZh.includes(line)) parts.push(line)`），
`理由` 改成 `!parts.some((l) => l.startsWith('理由：')) && !rawZh.includes('理由：')`。

教训：拼装式文案里「已有内容就整体跳过」是最容易埋雷的分支 —— 增量必须按行判断，不能按块。
单测 52 条（新增一条专测这个链路）。
