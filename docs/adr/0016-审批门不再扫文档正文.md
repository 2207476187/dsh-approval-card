# 0016 审批门不再扫文档正文

- 状态：已采纳
- 日期：2026-11-23
- 相关：`~/.dsh/profiles/desktop/plugins/dsh-hooks-shim/rules/gate-bridge.mjs`

## 背景

写一个 3 KB 的 ADR 到工作区内，弹出「目标含工作区外路径 1 处：…」。真实目标就在工作区内，一个字都没越界。同一批改动里，90 KB 的 devlog 却从不弹。

定位到 `dsh-hooks-shim` 的 `gate-bridge.mjs`：`flattenInput()` 除了路径字段（`PATH_KEYS`）与自由文本（`command`/`script`/…），还会把「其余所有**长度 ≤ 4000** 的字符串字段」拼进扫描块。于是 `write` 的 `content`、`edit` 的 `new_string` 都进了 `extractAbsolutePaths()`，正文里任何盘符字样或以斜杠开头的文件名都会被当成「命令里混着的路径」，`isInside()` 判成工作区外，R1 随即报越界。

「超过 4000 字符就不弹」这一点让现象极难自查：同一件事，短文档弹、长文档不弹，像是审批策略随机。

这条规则的本意是防「读后写得穿」——不许把目标藏在参数里蒙混。但它把**要写进去的内容**和**要动的目标**混成一类。

## 候选

- **A 保持现状，靠写法规避。** 正文里不写盘符字面量、不写前导斜杠片段，或干脆让正文超 4000 字符。
  代价：每份文档都得惦记，且误报是静默的——人容易以为真在写外部路径。
- **B 只加 `BODY_KEYS` 排除表。** `flattenInput()` 见正文字段即跳过。
  代价：正文不再参与任何判定，但 R1 仍会对 `write` 的自由文本做路径解析（此时自由文本只剩 `justification` 等短字段），语义仍然含混。
- **C（采纳）B + R1 按工具分流。** 结构化目标（`PATH_KEYS` 命中字段）所有工具都算数；自由文本里解析出的路径只对 `EXEC_TOOLS`（`pwsh`/`bash`/…）算数。`EXEC_TOOLS` 从函数内部提到模块级，R1 与 R4 共用同一个判定。
- **D 彻底关掉 R1 的文本扫描。** 只信结构化字段。
  代价：`pwsh` 命令里 `Remove-Item "某个盘符路径"` 这类「命令里混着路径」的常规形态会漏——那正是这条规则最该管的场景。

## 决定

采纳 C。两处改动都在 `gate-bridge.mjs`：

1. 新增 `BODY_KEYS`（`content` / `new_string` / `old_string` / `new_str` / `old_str` / `file_text` / `replacement` / `patch` / `diff` / `body` / `text`），`flattenInput()` 的「其余字段」分支见键即 `continue`。
2. R1 的路径集合改为 `new Set(fieldPaths)`，只有 `isExec` 时才并入 `extractAbsolutePaths(text)`。

## 代价

- 正文里真写着路径也不再提示。那本来不是「目标」——目标由 `file_path`/`target` 等字段表达；要写外部文件，`file_path` 一样会被拦（已用 case 2 验证）。
- `BODY_KEYS` 是一张手工清单。将来某个工具用新字段装正文（例如 `contents`、`payload`），还要补进去，否则误报会以新的名字回来。
- 命令类工具的行为完全不变：路径混在命令里照样解析、照样拦（case 3 验证）。
- 回归靠 `tools/verify-gate-path-scan.ps1` 四组用例；插件自带的 `test/selftest.mjs` 只覆盖 hooks 协议层，**覆盖不到这条判定**——两层测试都要跑。
