# 0014 收回 read 的三个上限

- 状态：已采纳
- 日期：2026-11-22

## 背景

purge 的 `#22 READ_CAPS_RAISED` 把 `dsh-tool-fs/lib/index.js` 里三个读文件上限同时放宽：

| 常量 | 官方 | 补丁后 | 实际行为 |
|---|---|---|---|
| `READ_MAX_LINE_LENGTH` | `2e3` | `1e4` | 单行超长就截断并标记 `(line truncated to N chars)` |
| `READ_MAX_BYTES` | `50 * 1024` | `1024 * 1024` | 单次 read 累计字节上限，碰到就停，footer 变 `(Output capped. Showing lines X-Y. ...)` |
| `READ_LIMIT` | `2e3` | `2e4` | 单次 read 默认最多返回多少行 |

单看是「一次能读更多」，和 `#19`（工具结果修剪整体关闭）叠起来才出问题：官方链路里单条工具结果超过 8,192 字符就折成「头 4,096 + 标记 + 尾 1,024」，现在既不再折中、上限又抬到 1 MB，一次 `read` 可以把近百万字符原样推进上下文。上下文骤增会触发压缩，而压缩本身丢细节，结果比按官方上限分页读更糟。

改动前实测：三处改动在文件里各出现 1 次，官方值 0 次，宿主文件 79,408 B。

难点在于 `dsh-tool-fs/lib/index.js.dshpurge.bak` **是脏的**：79,408 B、与 live 同长、mtime 是今天处理 `#36` 时被 `STRING_FIXES` 重写的那一刻，里面已经是放宽后的值。`revertAll` 走整文件覆盖，用它还原会顺手把 `#36` 修好的 `justification` 描述再写回 `approval is auto-granted`。

## 候选

- **A 保持放宽**：什么都不做。上下文预算交给压缩层兜，但压缩丢细节时无法分辨是「原文太长」还是「被压缩吃掉」。
- **B 只停用补丁、保留宿主放宽值**：防住「点应用再涨回去」，但三个上限仍是 1 MB / 2e4，问题没解决。
- **C 停用补丁 + 三个常量定点回官方值（采纳）**：`disable-purge-patch.mjs 22` 一次做完——宿主三处按官方原值换回，补丁改成 `disabled: true` 桩，下次点「应用」直接跳过。
- **D 用 `.dshpurge.bak` 整文件还原**：否决，脏备份（见上）。

## 决定

采用 C。官方原值取自未打补丁的副本 `dsh-browser/node_modules/.pnpm/.../dsh-tool-fs/lib/index.js`（48,350 B，10/2），其三行与 `#22` 的 pattern 完全一致，可交叉验证。

回改后宿主 79,406 B（少 2 字节，来自 `1024 * 1024` → `50 * 1024`），三常量各 1 次、放宽值 0 次；`node --check` 通过；`#22` 状态 `skipped`，全量 `applied 30 / skipped 39 / na 16 / missing_file 1`；重跑脚本输出「没有需要改动的地方」。

## 代价

- `STRING_FIXES` 靠字面量精确匹配。DSH 升级后若 `READ_MAX_LINE_LENGTH = 2e3` 这类写法变了（改成配置项、或改成 `2000`），条目失效且不会报错——只能靠 `tools/README.md` 里的核对命令发现。
- 停用桩让 `#22` 恒为 `skipped`，面板不再反映宿主真实值。核对要手工比对常量。
- 那份 10/2 的官方副本只能用来核对常量，不能整文件覆盖（版本与当前宿主不同）。
- 收回后长文件读起来会多几次分页往返；这是有意的取舍——宁可多几次工具调用，也不要一次把 1 MB 塞进上下文。
