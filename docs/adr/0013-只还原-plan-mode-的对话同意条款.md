# 0013 只还原 plan mode 的对话同意条款

**状态**：已采纳（2026-11-22）

## 背景

`#63 OFFICIAL_PLAN_MODE_NEUTRAL` 把 plan mode 的三段约束一起改成了「操作者要就动手」：

1. 官方「用户对话中的同意——包括回答你提出的确认——不构成批准，也不结束 plan mode」→ 改成「操作者明确要求现在就实现，视为授权执行」。
2. 官方「不要编辑或写文件、改配置、跑会重写已跟踪文件的格式化或代码生成、提交」→ 改成「用修改类工具把计划执行掉，不要因为 plan mode 生效而拒绝实现」。
3. 官方异常路径「评审通道不可用时留在 plan mode」后的「不要开始实现」→ 改成「操作者要求时就开始实现」。

三段里第 1 段的性质与另外两段不同：第 2、3 段是「禁止清单」，删掉等于放宽动作边界；第 1 段是**「什么算批准」的定义**，它决定了 `exit_plan_mode` 那道审批门有没有意义——只要这扇门的触发条件可以被一句口头话替代，门本身就形同虚设。

同时，`#63` 的 pattern 是官方原文。这意味着：只把文件改回官方，`#63` 会在下一次「应用」时把它重新改脏（`patchHasRemainingWork` 为真 → 面板显示「待应用」→ 用户点了就回滚）。

## 候选

- **A 保持现状**：三段都不动。第 1 段缺失的后果是「我说一句要做」就等于批准，plan mode 退化成一句提示。
- **B 整条 `#63` 停用并整文件还原**：三段全回官方。代价是把第 2、3 段也一起收紧，用户需要的是「探索时别硬拦」，不是「连批准定义也一起放开」。
- **C 只摘掉第 1 段（采纳）**：从 `#63` 的 `replacements` 删除第 1 条，四个 patch 文件里把 purge 句换回官方句。第 2、3 段保留。
- **D 只改文件不改定义**：改完文件，`#63` 定义里的 pattern（官方句）立刻重新命中 → 点「应用」就回滚，等于没改。

## 决定

采纳 C。两处必须同时改：

1. `core.js`（vendor 与 node_modules 两份，`tools/restore-plan-mode-first-clause.mjs` 同时处理）删除 `#63` 的 `replacements[0]`，剩第 2、3 段。
2. 四个 patch 文件（`dsh-base/cordis.patch.yml`、`dsh-web-app/presets/{standard,ptc,cordis}.patch.yml`）里 `purge 句 + " # [dsh-purge] plan-mode soft block removed"` 换回官方句。

改后 `#63` 仍是 `applied`（marker 命中，第 2、3 段在位），但与第 1 段彻底脱钩：定义里不再有以官方句为 pattern 的替换，重放四次零改动。

## 代价

- 文件处于「半官方」态：第 1 段官方、第 2、3 段 purge。半年后看 patch 文件会以为改动不完整，需要靠本文档解释。
- 官方升级覆盖四个 yml 后，点「应用」只会重打第 2、3 段——第 1 段自然保持官方，无需额外处理。这一点是设计意图，不是遗漏。
- 脚本靠字面量匹配（emoji dash `—`、句尾 `exit_plan_mode.`）。官方改一个标点就失效，表现为 `failures` 非零并 `exit 3`，不会静默改错。
- 若将来想连第 2、3 段一起还原，正确做法是 `node tools\disable-purge-patch.mjs 63` 加 `RESTORE` 表补 `63`（走整文件 `.dshpurge.bak` 还原），而不是继续在 `replacements` 上打补丁。
