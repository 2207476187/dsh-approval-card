# 0019 把 #42 的 legacy 设置写盘改成原子写

- 状态：已采纳
- 日期：2026-11-23

## 背景

`#42 SETTINGS_LEGACY_API` 给 `dsh-settings` 补回了旧版 `register(ns, schema)` / `get(ns)` API，服务对象是 vendored 的 `channel-pack`（`vendor/channel-pack/pack.js:29138`）——它把账号池写进 `~/.dsh/settings-legacy.yaml`，该文件当前 26,878 字节，只有 `channel-pack` 一个命名空间。

这条补丁不能收（收掉 `our-free-model` 的免费通道与已登录账号全部失效），但它插入的持久化写法有两个问题：

```js
await writeFile(this.legacyPath, stringify(this.legacyDocument), "utf8");
```

1. **非原子**：整个 YAML（含全部账号与 `credentialRef`）一次性覆写，中途失败就是残缺文件，账号池直接丢；
2. 官方其余落盘路径都是「写临时文件 → `rename`」，这一处是唯一例外。

另外 `#42` 的 12 条 replacements 里有 4 条的 pattern 在替换后仍然命中（pattern 是「保留原文 + 追加」，靠 `skipIfMarked` 的 marker `#89 ?? {} 兜 over=undefined 丢 base` 拦住重复应用），所以只改宿主文件、不改 `core.js` 里的 replace 文本，下次点「应用」就会被旧文本打回非原子写。

## 候选

- **A 保持现状**：不动。代价是账号池的写入一直是单点风险。
- **B 只在宿主文件改原子写**：点一次「应用」就退回去，等于没改。
- **C 宿主 + `core.js` 的 replace 文本同时改**（采纳）：两处文本保持一致，重放与应用都落到加固版。
- **D 收掉补丁、让 channel-pack 改走官方 configEditor**：要改第三方 vendored 代码（`pack.js`），面更大、且上游一更新就丢。

## 决定

采纳 C。新增 `.build/harden-legacy-write.mjs`，把那条语句换成三行：

```js
const tmpFile = this.legacyPath + "." + process.pid + ".tmp"; // [dsh-purge-hardening] atomic legacy write
await writeFile(tmpFile, stringify(this.legacyDocument), "utf8");
await rename(tmpFile, this.legacyPath);
```

`rename` 已在 `#42` 加过的 import 里，不新增依赖。脚本对三个目标各要求「原始语句恰好 1 次」，否则 `exit 3` 不写盘；写盘前备份 `.bak-<stamp>-atomic`。

验证：宿主 27,650 → 27,793 B，`tmpFile` 语句 / `writeFile(tmpFile)` / `rename(tmpFile)` 各 1 处、原来的整写 0 处，`node --check` 通过；两份 `core.js` 同步（同哈希 `B0DB555DEB7C2812`，354,491 B）且都含加固文本 1 处；单独对 `#42` 跑 `applyPatches` 得 `status: already / applied 0`，文件哈希前后一致。

## 代价

- 多一个 `.tmp-<pid>` 中间文件；写失败时会残留在 `~/.dsh` 下（正本不受影响）。
- `core.js` 又被本地改了一处（累计多处），purge 重装需重跑 `harden-legacy-write.mjs`；DSH 升级不影响——升级后点「应用」会按已加固的 replace 文本重新插入。
- 中间文件的 pid 命名意味着并发写不会互相覆盖，但也意味着不清理旧 pid 的残留。
